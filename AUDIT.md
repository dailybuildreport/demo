Эталон — БЦ «Раменки». Цель — один UX и один алгоритм при разных данных объектов.

## 2. Что сделано

**Одна кодовая база для обоих объектов.**
- `assets/dsflow-engine.js` — расчётный движок и все экраны «Раменок» (обзор, реализация, структура, этап, работа, Гант, вехи, календарь, бюджет, договор, фото, сравнение, ввод факта, ИИ). Параметры объекта — `PROJECT.engine`.
- `assets/dsflow-core.css` — дизайн-система «Раменок», вынесена из HTML и подключена обоим объектам.
- `ramenki/index.html` — только данные «Раменок» + общий движок. Расчёты и данные не менялись; экраны совпадают пиксель в пиксель, кроме слов «модели весов БЦ» → «модели весов объекта».
- `ogni/index.html` — новая страница «Огней» на том же движке. Данные: `assets/data/ogni-gpr.js` (1 488 строк ГПР из MS Project, 932 строки со связями, 4 вехи источника; генерируется `tools/build-ogni-gpr.py`), `assets/data/ogni-daily.js` (45 сводок, 23 цели, 8 испытаний, 83 события — без изменений), `assets/ogni-project.js` (настройки и данные объекта).

**Готовность проекта «Огней»** считается тем же алгоритмом, что у «Раменок». Согласованной модели весов нет, поэтому движок строит её автоматически по длительности ГПР (раздел — этап верхнего уровня, работа — его строка, вес — доля рабочих дней). Факт — процент выполнения из MS Project на 30.06.2026 плюс подтверждённые объёмы суточных сводок по трём работам с однозначной строкой ГПР: форшахта (fs_pct), стена в грунте (захватки из 44), БНС (сваи из 262). Метод указан на экране структуры.

Результат на 29.09.2026: готовность 1,7 % при плане 19,4 %, прогноз окончания 18.01.2030 (+280 дн. к 13.04.2029). **Важно:** ГПР сохранён 30.06; по 345 работам плановый срок уже прошёл, а факта по ним после 30.06 нет. Поэтому отставание и прогноз отражают устаревший график и отсутствие факта, а не обязательно реальное положение на площадке. Цифры станут точнее после загрузки актуального ГПР или ввода факта по работам.

**Раздел «Данные и отчёты» «Огней»** — исходное приложение суточного отчёта (`ogni/report.html`) без изменений расчётов: Производство, Журнал, Риски, Хронология, Отчёт. Оно встроено в общую оболочку одним экземпляром: хлебные крошки, боковая панель, мобильное меню, тема и история браузера общие; период, фильтры и графики сохраняются между переходами. Кнопки внутри отчёта («Сформировать отчёт» и т. п.) ведут через навигацию оболочки. Печать отчёта работает как раньше.

**Оперативный факт на уровне работы.** Карточки «Устройство БНС», «Стена в грунте», «Форшахта», «Обвязочная балка», «Испытания БНС» дополнены панелью «Оперативный факт площадки»: плановый объём, факт, план/факт на дату, темп за 7 суток и прогноз (расчёт `computeA` из суточного отчёта), суточная динамика, последние сводки, события, испытания, переход к графику «Производства». На этапе «Организация стройплощадки по ПОС» — откос, газовая труба, вывоз грунта, демонтаж форшахты, рабочая сила (на готовность не влияют).

**Бюджет «Огней»** — тот же компонент; договоров нет, поэтому везде «—» и пустой реестр. Значения не придумывались.

**Фото «Огней»** — та же хроника «Раменок». Загруженные ранее снимки читаются из той же IndexedDB (`dsflow-ogni-photos`). Загрузка в обычном браузере теперь сохраняется в IndexedDB у обоих объектов (у «Раменок» раньше терялась при перезагрузке).

**Внести данные ИИ** — одно окно у обоих объектов. В «Огнях» «Внести факт» открывает ввод показателей суточной сводки, «Загрузить отчёт ИИ» — разбор суточных отчётов (прежний алгоритм). Кнопка «Внести факт» на странице работы одинакова в обоих объектах: прирост % по строке ГПР с пересчётом проекта.

**Общее поведение:** одна тема на весь DSFlow (`dsflow.theme`), одна проверка версии установленного приложения (`assets/dsflow.js`), итоги объектов на стартовой странице пересчитываются при открытии объекта (`dsflow.summary.<id>`).

**Стартовая страница и верхняя панель.** Удалены «Проекты», «Объекты строительства», «Все проекты», «Разные объекты. Одна система управления» и подписи карточек «План реализации · Оперативный факт · Риски» / «Гант · Бюджет · Фотохроника». Шапка: **DSFlow | Управление проектами**, далее сразу карточки объектов. В верхней панели проектов ссылка «Проекты» заменена подписью «Управление проектами», пункт «Все проекты» — «Выбор объекта».

Удалены заменённые модули `ogni-management.js` и `ogni-photos.js`. Исходник `ogni-schedule.json` сохранён.

## 4. Выпуск dsflow.19: «Структура готовности» и администрирование графика

### Найденные различия
- **Таблица «Структура готовности объекта» у «Огней» разваливалась.** Причина — общий CSS: класс контейнера страницы `.wrap` совпадал с классом ячеек `td.wrap`, и ячейка получала `display:flex`, `margin:auto` и отступы 32 px. У «Раменок» это давало только сдвиг заливки строк, у «Огней» длинные названия этапов (до 300 символов) растягивали первую колонку за пределы экрана. Исправлено в `dsflow-core.css` для обоих объектов: правила контейнера ограничены `.main > .wrap`, длинные названия переносятся.
- В колонке «Ед.» у «Огней» стояло «раб. дн.» — это основа весов, а не единица измерения. Теперь «—».
- Плитка «Плановый объём» на странице работы у обоих объектов показывала «100 %» при отсутствии объёма. Теперь это объём и единица, если они есть в данных, иначе «—».

### Администрирование проекта (общий компонент движка)
- Вход: почти незаметная иконка ⚙ в правом нижнем углу боковой панели (подсказка «Администрирование»), в мобильном меню «Ещё» — такая же иконка. Вход подтверждается. В режиме — плашка «Режим администрирования · Правки · Выйти», оранжевая полоса у меню и пунктирная рамка рабочей области.
- Карточка работы: название, раздел/этап, начало, окончание, плановый срок (раб. дн., синхронизирован с датами), факт. начало и окончание, единица измерения (шт., м, п.м., м², м³, т, кг, %, дн., компл. или своя), плановый и фактический объём, количество, % выполнения (считается из объёмов, если они заданы), статус.
- «+ Добавить работу» — в разделе администрирования, в Ганте и в строке этапа. Новая работа — строка того же графика: появляется в Ганте, структуре, этапе, готовности и прогнозе.
- В Ганте в режиме администрирования: нажатие на строку открывает карточку, полосу можно тянуть (перенос), левый край — начало, правый — окончание.
- Скрыть (работа остаётся в данных, но не отображается и не считается) и удалить (мягкое удаление). Блок «Скрытые / удалённые работы» с кнопкой «Восстановить».
- Порядок работ (↑ ↓) и перенос в другой этап; массовый сдвиг сроков и массовое скрытие выбранных работ.
- Подтверждение: вход, добавление, удаление, скрытие, восстановление, перенос и порядок, массовые операции, сброс и загрузка правок. Изменение дат и объёмов проходит без подтверждения, но с кнопкой «Отменить».
- Журнал изменений, отмена последних 30 правок, файл правок (сохранить или загрузить) для переноса между устройствами.
- В обычном режиме все элементы редактирования скрыты.

### Единый источник данных графика
`S.admin` — один слой правок на объект (ключ `<префикс>admin` в браузере, в среде Claude — общая база проекта, коллекция `admin`). Функция `build()` накладывает его на исходный ГПР (`MPP_ROWS`), и один рассчитанный граф `M` читают Гант, структура, этап, работа, вехи, календарь, обзор, готовность и карточка на стартовой странице. Отдельной копии данных для Ганта нет. Исходные файлы ГПР не меняются.

### Проверено (оба объекта)
Вход с подтверждением → правка названия, % и единицы на странице работы → готовность в «Структуре» и на «Обзоре» пересчитана → добавление работы с собственной единицей «захв.» и объёмами 10/3 (30 %) → она в Ганте → перетаскивание (+13 дн.) и растяжение правого края (+9 дн.) → удаление и восстановление → сохранение после перезагрузки → выход (элементов редактирования нет) → сброс всех правок: готовность вернулась к исходной (37,33 % / 1,74 %). Ошибок JavaScript нет.

### 5.3. Универсальная модель
- **Работа** — строка графика (исходный ГПР или добавленная) + слой правок `S.admin` (название, этап, единица, общий объём,
  плановый объём на дату, накопленный факт, сроки, прогноз ответственного, статус, комментарий, скрыта / в архиве) +
  журнал факта `S.records`. Иерархия гибкая: проект → этап → раздел → работа; новый этап создаётся из обновления.
- **Веха, риск, событие** — записи `S.upd` с собственными ID (`В-001`, `Р-001`, `С-001`); вехи из данных объекта — ID `G<строка><s|f>`.
- **Договор** — `S.budget.contracts` (добавленные) или договор из данных объекта + `S.budget.meta` / `S.fin` (категория, статус, комментарий, оплачено, освоено).
- **Период обновления** — паспорт (тип, границы, дата актуальности, ответственный), заявленная готовность и итог периода сохраняются по периодам.
- **История** — `S.upd.history`: каждое обновление со старыми и новыми значениями, источником и исходным файлом.

- «Факт за период» прибавляется к накопленному; % выполнения считается из объёмов (СВГ 42 → 43 из 44: 95,5 → 97,7 %; БНС 96 + 10 → 106 из 262: 36,6 → 40,5 %).

- Договор из данных объекта: категория и «оплачено» меняются, сумма — нет (сообщение в проверке).

- Регрессия без обновлений: готовность «Раменок» 37,33 %, «Огней» 1,74 % — как до изменений; ошибок в консоли нет.

### 5.5. Ограничения
- Данные обновлений, как и остальные правки, хранятся в браузере (localStorage/IndexedDB) до подключения API и PostgreSQL. Исходные файлы обновлений — в IndexedDB этого браузера.
- Для «Раменок» действует согласованная модель весов: новый этап верхнего уровня, созданный обновлением, в неё не входит — проверка модели покажет его как работу без владельца, пока веса не согласованы.
- Фото в Excel описываются строкой с именем файла; сами файлы прикладываются при загрузке.
