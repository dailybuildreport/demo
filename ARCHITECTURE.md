# FLOW — Цифровой штаб строительства · демо-версия

Демонстрационная версия: пять вымышленных объектов в разной стадии строительства на одной архитектуре.
Рынок — девелопер и технический заказчик. Все компании, люди, адреса, объёмы и документы вымышлены и
корректируются в администрировании объекта («Настройки объекта → Контроль и отчётность» и другие вкладки).

```
объект → конфигурация → разделы → сущности/показатели → данные → универсальные компоненты интерфейса

data/projects/*.js        датасеты (исходные объекты демо, не изменяются)
assets/config.js          реестр объектов (DSF.registry), разделы, роли и права, организации, файлы (IndexedDB)
assets/store.js           журнал операционных действий (события, поручения, КС-2, письма, движение документов,
                          ежедневные отчёты и их подтверждение, замечания, решения по сигналам, причины отклонений)
data/flow/*.js            производственный контур демо-объектов: отчёты, ИД, замечания, гарантийные письма (DSF.augment)
        ↓
assets/engine.js          UNIVERSAL PROJECT ENGINE — сроки, готовность по правилам объекта, бюджет, КС-2, календарь, проверки
assets/engine-records.js  документы и редакции, протоколы → поручения, письма
assets/engine-flow.js     журнал ежедневного факта и цепочка подтверждения, темп, ИД по работам, гарантийные письма,
                          замечания стройконтроля, причины отклонений, сигналы штаба, хронология
        ↓
assets/ui.js              каркас, меню (по разделам объекта), Обзор, График, Риски, Фотохроника
assets/ui-work.js         Ресурсы, Календарь, Поручения, Документы, Бюджет → Договор → КС-2
assets/ui-flow.js         Производство, Качество, Хронология, штаб (сигналы и решения), карточка работы «почему», КС-2 ↔ ИД
assets/admin.js           «Добавить объект», «Настройки объекта», «Администрирование», внесение данных, Показатели
```


## 0. Подключение нового объекта без разработчика

**Где:** «Портфель» → кнопка «Добавить объект» (также в боковом меню и в карточке «Добавить объект» в списке объектов; маршрут `#new`). Доступно роли «Администратор системы».

Мастер из 12 шагов — любой шаг можно пропустить, обязательно только название; черновик сохраняется автоматически:
Основное (название, краткое, тип, статус, адрес, описание, даты начала/плана/факта, ТЭП, обложка, ответственные) →
Участники (организации из общего справочника, роли, контакты) → Разделы (какие разделы включены) →
График и вехи (этапы, работы, объёмы, план/факт, зависимости FS/SS/FF с лагом, вехи с директивными сроками, финальная веха) →
Готовность (правило: по стоимости / по весовым коэффициентам этапов и работ / вручную) → Бюджет и договоры →
Документация (разделы и подразделы РД/ПД, свои категории, предусмотренные документы) → Ресурсы (виды техники и оборудования, недельные данные) →
Контроль и отчётность (цепочка подтверждения факта, обязательность ИД, срок гарантийного письма, пороги сигналов) →
Ресурсы → Показатели (периодические показатели и их значения) → Риски → Фото → Проверка и создание.

После создания объект регистрируется в DSF.projects как описание (та же модель Project, что у датасетов), появляется в портфеле и
общей аналитике, получает рабочий стол и меню по выбранным разделам. Дальше всё меняется в **«Настройках объекта»**
(`#<id>.settings`, пункт меню «Настройки объекта»): те же редакторы + проверка данных, журнал изменений, архив/удаление.
Датасеты тоже можно настраивать: изменения сохраняются как редактируемая копия, исходник не меняется, есть «Сбросить к датасету».

Операционные данные вносятся в разделах объекта: «Подать ежедневный факт» (подрядчик, раздел «Производство»), «Корректировка факта» (администрирование, график), «Внести данные» (ресурсы), «Внести значения» (показатели),
«Загрузить фото», «Риск или проблема», в карточке договора — «Доп. соглашение», «Внести КС-2», «Оплата», в документах — «Загрузить документ».

**Целостность.** Каждое изменение проходит пробную сборку модели: правка, создающая цикл связей или новую ошибку данных
(например, % без фактического начала, фото раньше начала работы, КС-2 больше принятого), не сохраняется, причина показывается в форме.

**Ничего не придумывается.** Готовность без настроенных весов не рассчитывается («—»); финансы новых объектов считаются только
по введённым договорам, КС-2 и оплатам (`finance: 'entered'`), без модели актов; пустые показатели показываются как «—» или скрываются.

**Роли (демо).** Администратор системы (всё, включая любую ступень подтверждения), Директор проекта (подтверждение факта,
решения по сигналам штаба, настройки, график, бюджет), Технический заказчик (подтверждение факта, проверка и приёмка КС-2,
согласование ИД, замечания стройконтроля), Подрядчик (ежедневный факт, КС-2 и гарантийные письма, устранение замечаний),
Наблюдатель / инвестор (просмотр). Роли ТЗ и Директора в цепочке подтверждения меняются администратором объекта.
Кнопки недоступных действий не показываются, обработчики проверяют права повторно. Роль выбирается в карточке
«Пользователь (демо)» — входа в систему в демо нет.

**Хранение (демо-адаптеры).** Описания объектов, справочник организаций, журнал — localStorage (`dsf-registry`);
операционные записи — localStorage (`dsf-demo-store-<id>`); файлы — IndexedDB (`dsf-files`). Экспорт/импорт конфигурации — в «Администрировании».
Для серверной версии заменяются только `DSF.registry.load/save`, `DSF.store.adapter` и `DSF.files.put/get`.

## 1. Производственный и контрольный контур

```
Подрядчик: ежедневный отчёт (объёмы по работам, люди, фото)
   → ступени подтверждения в порядке, заданном администратором (по умолчанию: Технический заказчик → Директор);
     на любой ступени объём можно скорректировать или вернуть отчёт подрядчику с причиной
   → полностью подтверждённый факт: готовность работы, Гант, прогноз, выполнение договора, основание КС-2
Темп за 14 дней по подтверждённому факту → прогноз по темпу; прогноз работы в графике не раньше прогноза по темпу
КС-2 подрядчика → проверка ИД по работам заявки → без принятой ИД: предупреждение и гарантийное письмо со сроком
   → срок — событие календаря; при приёмке ИД письмо исполняется автоматически; просрочка — сигнал штаба
Замечание стройконтроля: выдано → назначено → в работе → предъявлено → закрыто (или возврат на доработку);
   критические и просроченные — в календаре, в карточке работы, в КС-2 и в штабе
Сигнал штаба (что, почему, кто отвечает) → решение директора: поручение (с контролёром) / риск / к сведению → хронология
```

Неподтверждённый факт нигде не учитывается как выполнение; он показывается отдельно («ждёт: …»).

## 2. Информационная архитектура

Одинакова для всех проектов. Меню: «Обзор» и раскрывающийся пункт «Подробно».

| Раздел | Что внутри |
|---|---|
| Обзор (штаб) | 4 KPI: Готовность, Срок, Бюджет, Ресурсы; контрольные блоки «Производство сегодня», «Деньги: КС-2», «Исполнительная документация», «Качество»; «Требует решения» — сигналы с причиной, ответственным и решением директора; компактный график; фотохроника |
| Производство | Журнал ежедневных отчётов с цепочкой подтверждения, пакетное подтверждение, возврат и исправление; темп и прогноз по темпу по работам |
| Качество / стройконтроль | Замечания с жизненным циклом, фильтры, аналитика по подрядчикам |
| Хронология | История проекта из всех разделов со ссылками на первичные объекты |
| Реализация / График работ | Гант: план/факт/прогноз, критический путь, вехи; карточка работы «почему» (причины отклонения из данных, темп, ИД, замечания, КС-2, причины и мероприятия участников) |
| Ресурсы | График движения рабочей силы (по умолчанию), по подрядчикам, техника |
| Календарь | Месяц / неделя / повестка; «что произошло ← сегодня → что предстоит»; события графика и события проекта; создание и редактирование событий; черновики писем и приглашений |
| Бюджет | Статьи → договоры → история КС-2 → карточка КС-2 с двухэтапным процессом |
| Документы | РД, ПД, ИД, КС, Отчёты, Письма, Протоколы, Разрешения, Договоры; разделы с подсчётами; карточка документа с редакциями и связями; загрузка |
| Протокольные поручения | Реестр с фильтрами, карточка поручения, протоколы-источники |
| Риски | Карта и реестр рисков, поручения по рискам, решения |
| Фотохроника | Снимки по работам и датам |

Маршрут: `#<проект>.<раздел>.<объект или вкладка>` — например `#kristall.budget.ks-kc3-6`, `#bereg.docs.d-...`, `#vostok.resources.wf`. Любой объект открывается по своей ссылке из любого раздела.

### Единые объекты и связи (без копий)

```
Протокол → Поручение → срок в Календаре → «Требует внимания» (если просрочено или критическое)
Работа ↔ РД (редакции, отметка «Передано в производство работ») ↔ событие «Выдача РД» ↔ поручение ↔ письмо
Работа → ИД (АОСР/АООК → событие освидетельствования) → приёмка → КС-2 → договор → статья бюджета
КС-2: Черновик подрядчика → Направлено → Проверяется ТЗ → (Есть замечания ↺) → Предварительно согласовано
      → «Назначить приёмку» (событие в Календаре, связь в обе стороны) → Принято / Частично / Не принято
      → КС-2 по принятому объёму → Согласовано → Расчётный период → Оплачено
```

Суммы по договору разделены: выполнено по графику, заявлено подрядчиком, принято ТЗ, КС-2 сформировано, согласовано, оплачено, остаток (= сумма − согласовано). Непринятая часть возвращается в «не предъявлено».

### Демо-поведение и backend

Датасеты не изменяются. Действия пользователя (события, загрузки и движение документов, поручения, КС-2, письма, отчёты, замечания, решения) пишутся в `DSF.store` как записи и операции, движок накладывает их при сборке модели. Хранение — через адаптер: `DemoAdapter` (localStorage браузера); для промышленной версии достаточно реализовать `load/save` к API. Файлы в демо живут только в памяти вкладки. Почта не подключена: письма формируются как черновики (копировать / сохранить в «Письма»), адреса электронной почты не подставляются и не выдумываются. Сброс демо-изменений — в «Проверке данных».

## 4. Модель данных Project

Производственный контур демо-объекта лежит в `data/flow/<id>.js` и накладывается на датасет функцией `DSF.augment(id, { taskPatch, reports, remarks, documents, letters })`;
файлы сформированы `tools/gen-flow.js` так, что подтверждённый факт сходится с готовностью объекта, а темп — с прогнозом графика.


Датасет содержит только факты, которые на реальном проекте вводят люди:

```js

  dates:  { start, planEnd },                                 // начало СМР и плановый ввод
  budget: { reserve, items: [{ code, name, budget, mode?: 'linear', inReadiness?: false }] },
  contracts: [{ id, no, date, contractor, subject, item, amount, adv, ret? }],
  tasks: [{ id, stage, name, ps, pf, as?, af?, pct?, cost, item, contract?,
            deps?: ['id', 'id:SS+20', 'id:FF+30', 'id:FS-3'],
```

## 5. Что вычисляет движок

- **Готовность** — доля выполненной стоимости работ (без проектирования и управленческих статей); план на дату — по плановым окнам работ.
- **Прогноз сроков** — прямой проход по связям FS/SS/FF: завершённые по факту, начатые — по остатку объёма от отчётной даты, будущие — не раньше плана, предшественников и отчётной даты. Реализующиеся риски добавляют дни к своей работе.
- **Критический путь** — обратный проход, резерв времени ≤ 0.
- **Вклад риска в срок ввода** — пересчёт прогноза без этого риска.
- **Бюджет** — выполнение договора = сумма договора × доля выполненной стоимости его работ; акты КС-2 закрываются 25-го числа, оплата через 30 дней; оплачено = непогашенный аванс + оплаченные акты − гарантийное удержание. Прогноз стоимости = договоры + незаконтрактованные работы + реализовавшиеся риски.
- **КС-2** — исторические акты закрываются по графику (25-е число); текущая заявка каждого договора проходит двухэтапный процесс (`DSF.KS_STATUS`, `DSF.KS_NEXT`); заявлено / принято / согласовано / оплачено считаются раздельно.
- **Документы** — актуальная редакция, редакция в производстве, заменённые редакции, подсчёты по разделам; события «Выдача РД» и освидетельствования формируются из документов.
- **Поручения** — статус «Просрочено» вычисляется по сроку и отчётной дате; срок поручения — событие календаря.
- **Календарь** — вехи, начала и окончания работ (прошедшие по факту, будущие по прогнозу), события проекта и пользователя, повторяющиеся совещания; лента «что произошло ← сегодня → что предстоит».
- **Ежедневный факт** — журнал отчётов, ступени подтверждения, корректировки; только подтверждённые объёмы прибавляются к факту на начало журнала; темп за 14 дней и прогноз по темпу.
- **ИД и КС-2** — состояние ИД по каждой работе (принята / частично / на проверке / с замечаниями / не передана), работы КС-2 без принятой ИД, гарантийные письма и их исполнение.
- **Сигналы штаба** — сдвиг критического пути, вехи позже директивного срока, темп ниже порога, отчёты без подтверждения, КС-2 без движения, КС-2 без ИД, просроченные гарантийные письма, РД к началу работ, критические и просроченные замечания, бюджет, поручения, реализующиеся риски; пороги — в «Контроль и отчётность».

## 6. Связность и проверка данных

Каждый факт хранится в одном месте и показывается везде одинаково: дата ввода, бюджет, процент готовности, статус работы — одно значение на всех экранах. `DSF.validate` проверяет датасет при загрузке (результат — в сайдбаре, «Проверка данных»):

- процент без фактического начала; 100% без окончания; окончание при проценте < 100;
- фактические даты и документы позже отчётной даты;
- сумма стоимостей работ статьи ≠ бюджету статьи; прогноз ≠ договоры + остаток + риски;
- работа выполняется без договора; оплачено больше суммы договора;
- связи с несуществующими работами, циклы;
- фото снято до начала работы или после её завершения;
- риски и события со ссылкой на неизвестную работу или статью;
- документы: повторы, даты редакций и передач в будущем, передача раньше загрузки, «передано» без даты;
- поручения раньше протокола, срок раньше постановки; письма, события и КС-2 со ссылками на несуществующие объекты.

Все пять датасетов проходят проверку без ошибок и предупреждений.

## 7. Как добавить объект датасетом (для разработчика, необязательно)

1. Скопируйте любой файл из `data/projects/`, переименуйте в `<id>.js`, заполните факты своего объекта.
2. Положите фото в `photos/` (имя файла = значение `file`).
3. Допишите `<id>` в `DSF.manifest` в `data/manifest.js` (и, если нужен демо-контур, в `DSF.flowManifest` с файлом `data/flow/<id>.js`).

Интерфейс, движок и вёрстку менять не нужно. Если в данных есть противоречие, оно появится в «Проверке данных».

## 8. Запуск

Статические файлы, сервер не нужен для логики — но браузеры не загружают скрипты по `file://` во всех режимах, поэтому удобнее любой статический сервер:

```
python3 -m http.server 8000   # затем http://localhost:8000
```

Фотографии — Unsplash (лицензия Unsplash), авторы указаны в просмотре фото. Все компании, люди, адреса и показатели вымышлены.
