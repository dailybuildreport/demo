# Flow — цифровой штаб строительства · архитектура

Адрес размещения — **dsflow.ru**. Название продукта — **Flow**, дескриптор — «Цифровой штаб строительства».
Приставка `ds`/`dsflow` осталась только в домене и технических именах (файлы `dsflow-*.js`, ключи хранилища,
столбец «ID DSFlow» в Excel-шаблоне — для совместимости с уже выгруженными файлами).

## 1. Два контура в одной системе

```
login.html (заставка, основной пароль) ──► /  (index.html, data-flow-mode="real")
                                            реальные объекты: БЦ «Огни», БЦ «Раменки»
          └─ кнопка «Демо-режим» (внизу слева) ──► demo/login.html (демо-логин) ──► demo/index.html (data-flow-mode="demo")
                                            вымышленные объекты, роль по логину
```

| | Реальный контур | Демо-контур |
|---|---|---|
| Вход | основной пароль (`POST /api/auth/login`, при недоступном API — прежняя проверка по хэшу) | логин/пароль демо (`POST /api/demo/login`) |
| Сессия | `sessionStorage['dsflow.session']`, токен `scope=real` | `sessionStorage['flow.demo.session']`, токен `scope=demo` |
| Данные объектов | рабочие модули объектов `ogni/work.html`, `ramenki/work.html` (как и раньше) | только сервер: `GET /api/demo/projects/{id}` с фильтром по роли |
| Действия пользователей | браузер (`flow-real-*`) и рабочий модуль объекта | журнал на сервере (`/api/demo/journal/{id}`), каждая запись проверяется сервером |
| Ключи браузера | `flow-real-…` | `flow-demo-…` |

Токены не взаимозаменяемы: демо-токен на `/api/projects` → 403, реальный токен на `/api/demo/*` → 403.
Демо-страницы не подключают охрану реального входа, реальные — не читают демо-сессию.

## 2. Единый движок и интерфейс (из демо-архитектуры)

```
public/flow/
  env.js             адрес API (один на сайт)
  session.js         контур, сессия, клиент API, синхронизация журнала демо с сервером
  store.js           журнал действий объекта (LocalAdapter — реальный контур, ServerAdapter — демо)
  engine.js          UNIVERSAL PROJECT ENGINE: сроки, готовность, бюджет, КС-2, календарь, сигналы
  engine-records.js  документы, протоколы, поручения, письма
  engine-flow.js     ежедневный факт и подтверждение, темп, ИД, гарантийные письма, замечания
  engine-changes.js  корректировки графика: маршрут согласования и анализ влияния (новое)
  config.js          разделы и группы меню, роли и права, реестр объектов, файлы
  bridge.js          реальный контур: модель рабочего модуля объекта → модель Project Flow (новое)
  ui.js, ui-work.js, ui-flow.js, admin.js   экраны (обзор, график, бюджет, документы, производство…)
  ui-roles.js        кабинет подрядчика, обзор инвестора, корректировки, база подрядчиков (новое)
  ui-real.js         бюджет и данные площадки реальных объектов «как в источнике» (новое)
  flow.css           дизайн-система Flow
```

Один и тот же код рисует демо-объекты и реальные объекты. Отличается только источник данных.

### Реальные объекты: «структура и алгоритм — как в демо, данные — только реальные»

`bridge.js` загружает рабочий модуль каждого объекта в скрытом фрейме с `?headless=1`. В этом режиме
`assets/dsflow-engine.js` только считает модель объекта (ГПР, записи факта, правки администрирования,
«Обновление данных», бюджет и КС из браузера, фото) и отдаёт её через `DSFEngine.legacy()`. Мост переводит её
в модель Project Flow:

| Flow | Источник (рабочий модуль объекта) |
|---|---|
| этапы и работы | этапы ГПР и их дочерние строки (план, факт. даты, %, прогноз, критическая цепочка) |
| готовность, план на дату, кривая | расчёт модуля объекта (`readiness.mode = external`); у «Огней» — по длительности ГПР, у «Раменок» — по модели весов |
| срок, прогноз ввода | прогноз модуля объекта (Огни: +280 дн., Раменки: +29 дн. на срезах 29.09 и 25.09) |
| вехи | вехи объекта |
| договоры, закрытие КС-2 | реестр договоров и закрытие по месяцам (Раменки); у «Огней» договоры не переданы — «Нет данных» |
| ресурсы | недельная численность |
| риски, события | реестр рисков и события из «Обновления данных» |
| фотохроника | только реальные фото и загруженные снимки; процедурные «демо-кадры» не передаются |

Чего нет в источнике, то показывается «—» / «Нет данных»: бюджет проекта, оплачено, ИД, замечания, ежедневные
отчёты подрядчиков Flow. Расчётных подстановок нет. Ввод данных реальных объектов — по-прежнему в рабочем модуле
(«Ввод данных объекта» в меню, кнопки «Ввод факта и обновление ГПР», «Договоры и КС-2 — ввод»); всё внесённое там
сразу отражается во Flow (проверено: запись факта меняет готовность во Flow после перезагрузки).

Прежние адреса `/ogni/` и `/ramenki/` открывают объект во Flow (`/#ogni`, `/#ramenki`). Рабочие модули —
`/ogni/work.html`, `/ramenki/work.html`; суточный отчёт «Огней» — `/ogni/report.html` (без изменений).

## 3. Структура проекта (одинаковая для всех объектов)

Обзор → **Планирование и график** (график/Гант, корректировки графика, календарь) → **Мониторинг строительства**
(производство, ресурсы, показатели, риски) → **Подрядчики и договоры** → **Бюджет и КС** → **Документы** (РД, ПД, ИД, КС,
письма, протоколы; исполнительная документация; протокольные поручения) → **Строительный контроль** → **Фотохроника** →
**Аналитика** (хронология) → **Администрирование** (настройки объекта; на уровне системы — добавить объект,
база подрядчиков, администрирование). Группы меню объединяют существующие модули, дублей нет.

| Логин / пароль | Роль | Что видит |
|---|---|---|
| admin / 1234 | Администратор (суперадминистратор) | всё; «Администрирование»: пользователи, роли, матрица прав, доступ к объектам, история |
| director / 1234 | Директор по строительству | управленческий контур, утверждение корректировок, смет, КС-2; базовый план |
| tech / 1234 | Технический заказчик | факт, приёмка, КС-2, первая ступень корректировок, ИД и её проверка, замечания |
| smeta / 1234 | Сметчик | «Сметы» и сметная проверка КС; объекты «Кристалл Парк», «Береговой», «Восток Терминал» |
| gip / 1234 | ГИП | ПД/РД: загрузка, редакции, статусы, «Передан в производство»; объект «Кристалл Парк» |
| investor / 1234 | Инвестор / зритель | только «Обзор» |
| contractor1…contractor38 / 1234 | Подрядчик (у каждой организации своя запись) | назначенные объекты и виды работ; свои договоры, сметы, КС-2, отчёты, документы |

Права — ячейки матрицы «раздел × действие» (`api/app/perms.py`): разделы Обзор, График, Календарь, Выполнение работ,
Документы, ИД, Стройконтроль, База подрядчиков, Договоры, Сметы, Бюджет и КС, Риски, Отчёты, Администрирование;
действия Просмотр, Создание, Редактирование, Удаление, Загрузка, Проверка, Согласование, Утверждение, Экспорт,
Управление настройками (+ «Роли и матрица прав», «Смена паролей», «Пароли администраторов» в Администрировании).
Права пользователя = права роли ∪ индивидуальные разрешения − индивидуальные запреты; интерфейс показывает
источник каждого права. Доступ к объектам: по роли (все / назначенные) или явный список; подрядчик — по назначениям.
Системные роли нельзя удалить, права роли «Администратор» защищены; последний активный администратор не может
быть отключён; суперадминистратора меняет только суперадминистратор. Все изменения — в журнале безопасности.
Прежние укрупнённые права интерфейса (`can('confirm')` и т. п.) отображаются на ячейки через `ALIAS`; сервер
проверяет ячейку при каждом действии (`validate_append`), интерфейс только скрывает недоступное.

**Пароли.** Единый механизм для всех ролей (`api/app/accounts.py`): хеш PBKDF2-HMAC-SHA256 с солью; пароль и хеш
наружу не передаются, администратор задаёт новый пароль (дважды) и не видит текущий. Смена пароля увеличивает
версию `pv` — ранее выданные токены пользователя перестают действовать (401). Свой пароль пользователь меняет сам
с вводом текущего. Пароли администраторов — отдельное право. В журнал пишется факт смены, без пароля.

## 5. Сроки: календарно-сетевой расчёт (CPM) и корректировки

Единственный механизм расчёта сроков — `public/flow/cpm.js` (используют движок, анализ влияния, перенос начала,
импорт). Модель связи: `{pred, type: FS|SS|FF|SF, lag (дни, в т. ч. отрицательный), active, source: import|manual|change,
calendar}`; строковая запись `k05:SS+15`. Проверка сети: циклы, дубли, ссылки на несуществующие работы, работы без
предшественников / последователей → состояние `ok | partial | none | error`.
Прямой проход: ES/EF с учётом связей, рабочего календаря (`7d` или `5d` с праздниками), фактического начала и
окончания, ограничений «начало не ранее» / «окончание не ранее» (рабочий прогноз). Обратный проход: LS/LF, общий и
свободный резерв, критический путь (резерв 0 на пути к финальной вехе).

```
Подрядчик: запрос (работа, предлагаемые даты, причина, обоснование)
   → Технический заказчик: согласовать / вернуть / отклонить
   → Директор: утвердить / вернуть / отклонить
   → утверждённые даты становятся ограничениями РАБОЧЕГО ПРОГНОЗА; базовый план не меняется
   → базовый план меняется только отдельным действием «Базовый план → Новая версия» (право «График: настройки»)
```

`DSF.changeImpact` — сценарий «как если бы утвердили» тем же CPM, 9 блоков: изменение работы, резервы, критический
путь, последующие работы, этапы, вехи и директивные сроки, подрядчики, ввод объекта, достоверность расчёта; плюс
сравнение «До / После». Если связей нет или работа без последователей — «Недостаточно данных для достоверной оценки
влияния на ввод объекта. Требуется проверка логических связей графика»; цикл — ошибка расчёта, вывод о вводе не делается.
Статус объекта в портфеле — прогноз ввода против директивного срока: зелёный ≤ 0, жёлтый до 30 дн., красный больше.

Корректировка графика по слоям (`ui-plan.js`, журнал `taskOps`/`linkOps`/`baselineOps`): факт, рабочий прогноз,
базовый план, свойства, связи — каждая запись с основанием, автором и прежними значениями. Перенос даты начала
проекта: не начатые работы сдвигаются и пересчитываются по связям, начатые и подтверждённый факт не меняются,
создаётся новая версия базового плана. Импорт MS Project — XML (MSPDI): работы, суммарные задачи (этапы), вехи,
даты, % и связи FF/FS/SF/SS (`Type` 0–3) с задержками (`LinkLag`, десятые доли минуты); формат .mpp не читается.
После импорта — проверка связности и предупреждение о неполных связях.

## 6. КС-2 (двухэтапная схема — без изменений)

Этап 1 — на приёмку: черновик подрядчика → проверка ТЗ → замечания ↺ → предварительно согласовано → приёмка
(принято / частично / не принято). Этап 2 — оформление КС по принятому объёму: сформирована → согласована →
расчётный период → оплачено. Без принятой ИД — предупреждение и гарантийное письмо со сроком (контроль в календаре).

## 7. Как добавить объект

Демо: файл `api/demo_data/src/projects/<id>.js` (+ `src/flow/<id>.js`), id в `api/demo_data/manifest.json`,
`node tools/export-demo-data.js`. Реальный: рабочий модуль `<id>/work.html` на общем движке и запись в `REAL`
(`public/flow/bridge.js`); список активных объектов берётся из `/api/projects`. В интерфейсе — «Добавить объект»
(объект хранится в браузере).

## 8. Подрядчики, виды работ, договоры, сметы

Вид работ, подрядчик и договор — отдельные сущности: назначение `Объект → Вид работ → Подрядчик` (с зоной
ответственности, работами графика, договорами — необязательно). Исключение не удаляет историю (назначение
закрывается датой). Смена подрядчика не меняет расчёт сроков. Форма нового подрядчика — по шагам: организация →
объекты → виды работ (поиск, выбор нескольких, добавление нового вида без дублей и без фиктивных работ) → проверка.

Финансовая цепочка: Контрагент → Договор → Смета → Виды работ → График → Выполнение → КС-2/КС-3 → Освоение.
Договор регистрируется в «Бюджет и КС» и сразу участвует в расчётах; изменения — с основанием, история хранится.
Смета: разделы, позиции (работа / материал), НДС, версии; статусы Черновик → На проверке → Есть замечания /
Возвращена → Проверена сметчиком → Утверждена. КС-2 — по позициям утверждённой сметы, превышение объёма —
предупреждение. КС-3 — по периодам из принятых КС-2. Освоение = принято / актуальная стоимость договора × 100 %;
оплаты учитываются отдельно. В демо — демонстрационные сметы по всем договорам (`tools/demo-estimates.js`, «ДЕМО»);
в реальных объектах — «Смета не загружена». Общей функции сброса нет: журнал только дополняется.

## 9. Документы

Реестры (`ui-reg.js`, журнал `regdocs`/`regdocOps`, файлы — `/api/demo/files` с проверкой доступа):
ПД/РД (раздел → комплект → документы, редакции, «Передан в производство»; перечень разделов редактируется),
ИД (АОСР, исполнительные схемы, журналы, акты), приказы о назначении ответственных, документы о качестве
(сертификаты, паспорта), паспорта оборудования. Документы связаны с видами работ, работами графика, договорами и
друг с другом. Просмотр: PDF (pdf.js), изображения с масштабом, DOCX (mammoth), XLSX (SheetJS); DWG — скачивание.

Проверка документов: «по правилам» выполняет сервер (`/api/demo/check`) — наличие файла и реквизитов, сроки,
связи АОСР с РД в производстве, документами о качестве, схемой и приказом; результат помечен как автоматическая
проверка, подлинность не устанавливается. ИИ-проверка — только при подключённом сервисе (`FLOW_AI_URL`), иначе
сервер отвечает 503 и статус «Проверка не выполнена» не меняется; подставить «результат ИИ» из интерфейса нельзя.
Решение «Проверено специалистом» / «Отклонено» записывает специалист.
Демо-комплект «Кристалл Парк»: `python3 tools/make-demo-docs.py` (договор КП-26/МР-015, ПД КР, РД КЖ-01…03, АР-01,
ОВ-01, ВК-01, ЭОМ-01, приказы, АОСР, схема, журнал, паспорта, сертификат, паспорт оборудования, акт передачи РД);
все файлы помечены «ДЕМО — НЕ ДЛЯ ПРОИЗВОДСТВА РАБОТ», без печатей, подписей и реальных номеров.

## 10. Интерфейс на телефоне

Нижняя навигация: вне объекта — Портфель | Проекты | Календарь | Уведомления | Ещё; в объекте — Обзор | График |
Календарь | Документы | Ещё. Переключатель объекта — в заголовке. График — режимы «Список» (по умолчанию на
телефоне) и «Гант» (день / неделя / месяц / квартал / год, стрелки связей). Модальные окна: фон не прокручивается,
позиция страницы восстанавливается, заголовок и кнопки закреплены, безопасные зоны экрана учтены.
